# 第5章 系统测试与结果分析

## 5.1 功能测试

### 5.1.1 功能测试目标与方法

本系统功能测试的目标是验证“计算思维学习助手”核心业务链路的完整性、正确性与稳定性，重点覆盖用户认证、代码分析、对话问答、知识检索、学习分析与用户管理等关键模块。测试采用“自动化回归 + 前端交互验证 + 权限边界检查”结合的方式，在不依赖真实外部大模型与向量服务的前提下，通过桩件与模拟对象隔离外部波动，从而保证测试结果可复现、可比较。

测试执行命令如下（在项目根目录运行）：

C:/Users/30485/anaconda3/python.exe -m pytest backend/tests/test_text_processor.py backend/tests/test_vector_service.py backend/tests/test_rag_degradation.py backend/tests/test_api_integration.py -q

最新一次执行结果为：14 passed，11 warnings，耗时 2.31s。

### 5.1.2 功能测试覆盖设计

为全面展示项目功能，功能测试按照“用户使用路径 + 核心能力模块 + 角色权限边界”组织，具体包括以下七类。

1. 用户认证与会话鉴权功能。
   验证登录接口、令牌签发、鉴权访问流程是否正确，重点检查登录成功后令牌可用于受保护接口访问。

2. 代码分析功能。
   验证代码提交、语法与结构特征提取、综合分析结果返回是否完整，检查响应结构中状态字段、评分信息、建议列表等关键字段。

3. 流式问答功能。
   验证对话流接口的事件流格式与结束标记，检查流式输出在正常路径下是否包含完成信号，并保证异常情况下不会造成接口阻塞。

4. 文本处理与向量检索功能。
   验证文本切分、知识片段过滤、向量服务查询参数拼装与结果过滤逻辑，确保检索链路在不同输入条件下行为一致。

5. RAG 退化与鲁棒性功能。
   验证高置信度、中置信度、低置信度与兜底模式下的提示构建与返回策略，保证当检索质量下降或上下文不足时，系统仍可返回可解释的响应。

6. 学习分析模块功能。
   验证学习分析看板与学情报告链路，包括概览卡片、趋势图、活跃热力图、知识块热度排行、报告生成与导出。重点检查教师/管理员角色可见性、学生选择联动、周期切换（7/30/90天）与数据刷新行为是否正确。

7. 用户管理模块功能。
   验证管理员侧用户全生命周期管理能力，包括用户新增、编辑、角色调整、启用/禁用、删除，以及师生关联关系配置。重点检查权限控制与安全约束（如不能删除自己、不能禁用自己、不能非法越权）是否生效。

### 5.1.3 功能测试结果与分析

从结果上看，功能测试在当前版本达到以下结论：

1. 认证与鉴权链路完整。
   登录后可获取有效令牌，受保护接口访问符合预期，未出现鉴权失效或错误放行。

2. 代码分析接口稳定。
   输入代码后可稳定返回结构化分析结果，状态字段一致，响应结构未出现缺失。

3. 流式问答链路可用。
   接口可持续输出流式分段数据并正常结束，满足前端实时显示需求。

4. 检索与文本处理行为一致。
   文本处理、向量查询和过滤逻辑在测试输入下均满足预期，不存在明显边界行为异常。

5. 降级策略有效。
   在不同置信度场景下系统可按预设策略回退，避免“无结果即失败”的硬中断问题，提高了教学辅助场景的可用性。

6. 学习分析模块功能完整且角色边界清晰。
   教师/管理员可进入学习分析标签页，完成学生切换、周期切换、趋势与热力图查看，并生成学情报告；学生端不暴露管理视图，满足教学管理场景的最小权限原则。

7. 用户管理模块具备可操作性与安全性。
   管理员可完成用户增删改查与角色/状态管理；关键高风险操作具备约束规则，避免对当前登录管理员自身造成误操作，系统管理链路可控。

## 5.2 性能测试

### 5.2.1 性能测试方案与脚本体系

为保证性能测试可重复、可扩展，本项目构建了“单场景压测 + 多场景矩阵压测 + 自动出图汇总”的脚本体系：

1. 单场景脚本。
   文件为 backend/tests/load/run_performance_suite.py，用于一次压测并输出单次图表与报告。

2. 多场景矩阵脚本。
   文件为 backend/tests/load/run_performance_matrix.py，可连续执行 baseline、standard、stress 多档并发场景，并输出横向对比图和总报告。

3. 图表生成脚本。
   文件为 backend/tests/load/generate_charts.py，负责将 Locust CSV 自动转换为论文可用图表与 JSON 汇总。

4. 压测流量模型。
   文件为 backend/tests/load/locustfile.py，覆盖健康检查、登录、代码分析、流式问答四类请求。

5. 压测服务桩。
   文件为 backend/tests/load/mock_backend_server.py，通过替换外部依赖降低网络抖动影响，使测试更聚焦后端架构本身。

### 5.2.2 实际执行与产物生成

本章采用三场景矩阵压测，参数如下：

- baseline：20 用户，5 用户/秒，15s

### 5.2.4 性能结果分析

从结果可得以下结论。

1. 系统具有稳定的并发扩展能力。
   吞吐率从 baseline 的 28.38 req/s 提升到 stress 的 49.32 req/s，说明在并发提升时系统仍能扩展处理能力。

2. 响应时延随负载增加而上升，符合预期。
   平均响应时间从 54.55ms 上升到 302.57ms，P95 从 200ms 上升到 1000ms，表明高并发下存在明显排队与资源竞争。

3. 可用性保持在高水平。
   在最高并发场景下成功率仍为 99.91%，系统未出现崩溃或大面积请求失败，说明整体服务稳定性较好。

4. 高负载场景存在优化空间。
   压力场景出现少量认证失败（401），提示在更高并发下登录链路、令牌处理与队列峰值控制仍可进一步优化。

### 5.2.5 本章小结

本章围绕功能与性能两条主线完成系统测试。功能测试显示，用户认证、代码分析、流式问答、向量检索、学习分析与用户管理模块均能稳定工作，且角色权限边界清晰，核心用例全部通过。性能测试基于自动化脚本完成多场景压测与自动出图，在 50 并发用户压力下系统成功率达到 99.91%，吞吐率达到 49.32 req/s，验证了系统在教学辅助场景中的工程可用性。同时，测试也识别出高负载下时延增长与少量认证失败问题，为后续架构优化与性能调优提供了明确方向。
